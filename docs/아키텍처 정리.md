# 총정리 — `core` 결정의 정당화

## 1. 왜 DDD를 적용하나

복잡한 비즈니스 로직을 코드로 다룰 무기가 필요해서 + 사람이 쓰는 말과 코드가 일치하도록.

모멘텀은 차트 패턴 분석, 베이스 식별, 점수 계산, 리짐 판정 등 도메인 로직이 풍부하다. CRUD 앱이 아니므로 DDD 적용이 정당화된다.

**과한가 적당한가의 기준**

- 전술적 DDD는 **로직 복잡도**에 비례
- 전략적 DDD는 **조직 분리 압력**에 비례
- 이 케이스는 로직 복잡도 ↑ + 조직 압력 ↓

**결론**

- 전술적 패턴(값 객체, 엔티티, 어그리게잇, 도메인 서비스, 리포지토리)은 **적극 활용**
- 전략적 패턴(BC 분리, 컨텍스트 매핑, 모델 분리)은 **보류**

---

## 2. 도메인 서비스 vs 어플리케이션 서비스

**구분 기준**

도메인 서비스는 "비즈니스 규칙", 어플리케이션 서비스는 "유스케이스 흐름". 트랜잭션 경계, 외부 시스템 호출, 입출력 변환은 어플리케이션 서비스 책임.

**도메인 서비스의 데이터 조회 의존성**

분기에 따라 조회가 달라지면 그게 곧 도메인 지식이므로 도메인 서비스에 의존성을 둬도 된다. 단, **엔티티와 값 객체에는 절대 안 됨**.

**반환 정책**

도메인 서비스는 결과를 반환만 하고 저장은 안 한다. 저장은 어플리케이션 서비스나 쓰기 단계에서. 청크 트랜잭션 보호와 테스트 단순성 때문.

**어플리케이션 서비스의 자리**

유스케이스 흐름은 진입 채널마다 다름. HTTP 요청 단위, 배치 청크 단위, 실시간 틱 단위가 모두 다른 경계를 갖는다. 따라서 어플리케이션 서비스는 `core`가 아니라 `apps/*/application` 아래에 산다. 트랜잭션 경계도 거기서 잡힌다.

## 3. DDD 핵심 개념 판단법

| 개념 | 판단 기준 |
|---|---|
| **값 객체** | 같은 값들에 대한 비교/검증/계산이 반복되면 후보. 식별자 없고 불변. |
| **엔티티** | 식별자 있고 시간에 따라 변함. |
| **어그리게잇** | 트랜잭션 경계가 핵심. 작게 유지. 다른 어그리게잇은 식별자로만 참조. |
| **바운디드 컨텍스트** | 같은 단어가 같은 의미로 통하는 범위. 의미가 갈라지면 분리 신호. |
| **서브도메인** | 비즈니스 영역 분류(코어 / 서포팅 / 제네릭). |

## 4. 모듈 구조 — 프로젝트 컨벤션과의 충돌

**기존 정의**

- `apps` : 실행
- `modules` : 도메인 무관 공통
- `supports` : 보조

이 정의는 깨끗함.

**문제**

데이터 조회 구현체는 도메인을 알아야 작성됨. `modules` 정의("도메인 무관")에 안 맞음. 그렇다고 한 앱 안에 두면 다른 앱이 못 씀.

**해결 방향**

도메인과 도메인 의존적 인프라를 묶을 새 카테고리가 필요함.

## 5. 모델 분리는 안 하는 이유

### 5.1 언제 분리가 정당화되는가

- 같은 단어를 부서/팀마다 **다른 의미**로 쓸 때
- 팀이 다를 때
- 변경 주기가 다를 때
- 스케일링 패턴이 다를 때

대형 이커머스, 은행, 의료시스템처럼 조직과 규제와 스케일이 갈라지는 환경에서 효용이 큼.

### 5.2 주식 도메인 예시 — 대형 증권사라면

같은 "주식"이라는 단어가 부서마다 다른 의미를 가진다.

| 컨텍스트 | "주식"의 의미 | 핵심 속성 | 변경 주기 | 스케일링 |
|---|---|---|---|---|
| **거래 (Trading)** | 주문 가능한 상품 | 호가창, 체결, 수수료, 잔고 | 밀리초 | 초당 수만 건 주문 |
| **시장분석 (Analytics)** | 차트로 분석하는 대상 | 캔들, 패턴, 점수, 리짐 | 일 / 주 | 대용량 배치 |
| **기업분석 (Fundamental)** | 기업 지분 | 재무제표, 배당, EPS, PER | 분기 / 연 | 정적 데이터 |
| **포트폴리오 (Portfolio)** | 보유 자산 | 평가금액, 평균단가, 손익률 | 실시간 갱신 | 사용자별 분리 |
| **컴플라이언스** | 규제 대상 | 투자등급, 한도, 거래 가능 시간 | 규정 변경 시 | 규정 단위 |

같은 "삼성전자"를 다섯 부서가 다섯 가지 모델로 본다. **종목코드는 식별자로만 공유**하고, 모델 자체는 각자 자기 컨텍스트에 맞게 다르게 갖는다.

- 거래 부서가 PER을 알 필요 없음
- 분석 부서가 호가창 마이크로구조를 알 필요 없음
- 컴플라이언스 부서가 캔들을 알 필요 없음

이런 환경에서는 모델 분리가 정당화된다. 부서가 다르고, 변경 주기가 다르고, 스케일링 패턴이 다르고, 도메인 전문가가 다르기 때문.

### 5.3 모멘텀 케이스에서는 왜 안 그런가

실시간 / 배치 / API가 보는 "삼성전자"는 모두 같은 모델이다.

```
실시간  →  시세 수신
   ↓
배치    →  지표 계산, 베이스 식별, 점수 산출
   ↓
API     →  사용자 조회
```

같은 데이터의 **라이프사이클을 시간 순서대로 다른 진입점에서 만지는 것**뿐. 누가 봐도 "삼성전자"는 같은 실체이고, 호가창이라든가 PER 같은 구조적으로 다른 모델 표현이 등장하지 않는다.

### 5.4 분리의 진짜 비용은 데이터 동기화

식별자 전달은 비용이 거의 없지만, 데이터 동기화는 아래를 모두 신경 써야 한다.

- 최신성 보장
- 순서 보장
- 누락 방지
- 중복 처리
- 부분 실패 대응
- 스키마 변화 대응

여기엔 메시지 큐, 아웃박스 패턴, CDC, 스키마 레지스트리 같은 인프라가 줄줄이 따라온다.

**핵심**: 진짜로 분리해서 얻는 효용(팀 독립성, 변경 격리, 스케일 분리)이 비용보다 클 때만 분리가 정당화됨. 작은 조직이나 1인 개발에서는 효용이 작아서 비용만 남는다.

## 6. 모멘텀 케이스의 정체

**조건**

앱이 세 개로 나뉘어 있지만 "주식"의 의미가 어디서나 거의 같음. 같은 DB 공유. 쓰기 영역 자연스럽게 분리됨.

**의미가 같다는 것이란**

같은 실체를 같은 그림으로 본다는 것.

- 종목코드, 종목명 같은 **본질적 정체성**이 동일
- **라이프사이클**이 같음
- 한 도메인 전문가가 부서를 옮겨도 같은 단어를 같은 뜻으로 씀

이 케이스에서 실시간 / 배치 / API가 보는 "삼성전자"는 모두 같은 실체. 다만 그 위에서 보고 싶은 정보(시세인지, 분석결과인지, 검색결과인지)가 다를 뿐. **본질은 같고 관점만 다른 상태**.

**진단**

바운디드 컨텍스트 분리 문제가 아니라 **실행 환경 분리 문제**. 본질은 모놀리식인데 배포만 기능별로 쪼갠 형태.

**의미**

동기화 메커니즘이 필요한 상황 자체가 발생하지 않음. 도메인을 공유해야 자연스럽고, 그 도메인을 떠받치는 인프라(데이터 조회 구현체)도 함께 공유되어야 함.

## 7. 그래서 `core`가 답인 이유

### 도메인 공유 + 도메인 의존적 인프라 공유 = 한 묶음

도메인을 공유하기로 한 이상, 그 도메인을 데이터베이스에 매핑해주는 구현체도 자연스럽게 공유 자산이 된다. 둘은 본질적으로 같은 묶음. 분리해서 따로 관리하면 의존성만 복잡해질 뿐 얻는 게 없음.

### `modules` 정의를 깨지 않음

`modules`는 "도메인 무관 reusable configuration" 자리. 도메인 의존적 구현체를 거기 넣으면 정의가 흔들림. `core`라는 별도 카테고리를 두면 `modules` 정의는 그대로 유지되고, 도메인 의존적 자산은 자기 자리를 갖게 됨.

### 모든 앱이 공유 가능

기존에 한 앱(`stock-api`)에 박혀 있던 데이터 조회 인터페이스와 구현체는 다른 앱이 못 썼다. `core`로 옮기면 실시간 / 배치 / API 모두가 자연스럽게 공유. 비정상적인 역방향 의존이 사라짐.

### 전술적 DDD와 정합

도메인 모델, 값 객체, 어그리게잇, 도메인 서비스, 리포지토리 인터페이스 / 구현체가 한 곳에 모이면 도메인 로직 변경 시 한 모듈 안에서 응집도 있게 작업 가능. 전술적 DDD의 효용을 가장 잘 끌어냄.

### 전략적 DDD를 강요하지 않음

BC 분리 같은 무거운 결정 없이 그대로 하나의 도메인으로 다룰 수 있게 함. 미래에 진짜로 의미가 갈라지거나 조직 압력이 생기면 그때 `core` 안에서 다시 쪼개면 됨. **지금 미리 쪼개서 비용 부담할 이유 없음**.

## 8. 최종 모듈 구성

```
apps      : 실행 단위 (SpringBootApplication, Controller, BatchJob, WS handler,
            application 서비스, 트랜잭션 경계)
core      : 도메인 + 도메인 서비스 + 도메인 의존적 인프라 (Repository 인터페이스 / 구현체)
modules   : 도메인 무관 reusable configuration
supports  : 보조 기능 (logging 등)
```

기존 카테고리 정의는 모두 보존. `core` 한 줄 추가로 도메인-인프라 묶음 자리를 명확히 함.

### 8-1. `core` 내부 패키지 구조

```
core/
  domain/          엔티티, 값 객체, 도메인 서비스, 레포지토리 인터페이스(port)
  infrastructure/  레포지토리 구현체(adapter), JpaRepository, QueryDSL impl
```
