### 0-4. 부품 실측 — 외부 API 1건

일회용 테스트로 LS 캔들 API 1건을 5회 호출해 평균 응답시간 측정 (재무 API도 동일 요령).
→ 예측표의 "API 1건" 칸.

### 0-5. 베이스라인 잡 실행

배치는 `@Scheduled` 기동이므로 수동 실행은:

```bash
./gradlew :apps:stock-batch:bootRun --args='--spring.batch.job.enabled=true --spring.batch.job.name=dailyStockJob baseDate=2026-07-09'
```

- `baseDate`는 직전 거래일. 같은 파라미터 재실행 시 COMPLETED로 스킵되면 baseDate 변경.

끝나면 메타테이블로 스텝별 시간 (0-2 로그와 교차 확인):

```sql
SELECT step_name,
       TIMESTAMPDIFF(SECOND, start_time, end_time) AS sec,
       read_count, write_count
FROM BATCH_STEP_EXECUTION
WHERE job_execution_id = (SELECT MAX(job_execution_id) FROM BATCH_JOB_EXECUTION)
ORDER BY sec DESC;
```

**기록**:

| step_name | sec | read_count | 아이템당(ms) = sec×1000÷read |
|---|---|---|---|

### 0-6. 예측표와 목표값

**예측표** (부품 실측 × 구조 공식):

| 부품 | 실측값 | 공식 | 스텝 예측치 |
|---|---|---|---|
| LS 캔들 API 1건 | ___ms | × 종목 수 | ___분 |
| 재무 API 1건 | ___ms | × 종목 수 | ___분 |
| 계산 청크 1개(50건) | 베이스라인 sec ÷ 청크 수로 역산 | × 청크 수 | ___분 |
| SSE send 1건 | ___ms (STEP 2에서) | × 구독자 수 | 지연 ___ms |

**예측 vs 실측 판정**:
- 일치(±20%) → 병목 = 순차 API 호출 구조 확정 → STEP 1 카드 A+B
- 실측 ≫ 예측 → 숨은 원인 → STEP 1-2 (p6spy)

**목표값 (측정 전에 못 박기, 근거 한 줄씩)**:
- 배치: `가용 시간창 ÷ 재실행 여유` — 예) 창 2시간, 재실행 1회 여유 → 1시간 이내
- SSE 지연: 실시간 시세 체감 기준 — 예) p95 200ms 이하
- SSE 구독 수: `예상 사용자 × 동시 접속 비율 × 피크배율 × 안전계수` — 계수는 직접 정하되 근거 필수.
  예) 1,000 × 10% × 3 × 3 = 900 ≈ 1,000

**✅ 완료 조건**: 기록에 ①스텝별 시간표 ②예측표 ③목표값

### 1-3. 카드 A — Flow split (스텝 간 병렬, 보조, 30분)

`dailyStockJob()` 교체:

```java
@Bean
public Job dailyStockJob() {
  Flow candleFlow = new FlowBuilder<SimpleFlow>("candleFlow")
      .start(stockCandleStep())
      .next(stockPricePointStep())
      .next(stockVcpStep())
      .next(stockRegimeStep())
      .next(stockMaStep())
      .next(stockRsStep())
      .build();

  Flow epsFlow = new FlowBuilder<SimpleFlow>("epsFlow")
      .start(stockEpsStep())
      .build();

  Flow splitFlow = new FlowBuilder<SimpleFlow>("splitFlow")
      .split(new SimpleAsyncTaskExecutor("split-"))
      .add(candleFlow, epsFlow)
      .build();

  return new JobBuilder("dailyStockJob", jobRepository)
      .start(splitFlow)
      .next(stockRankScoreStep())     // 위치는 1-1 결과에 따름
      .end()
      .build();
}
```

**확인**: 로그에서 candle과 eps가 동시에 시작.

### 1-4. 카드 B — candle 스텝 파티셔닝 (스텝 내 병렬, 주인공, 반나절)

**(1)** LS API 초당 호출 제한 확인 → gridSize 결정 (모르면 2부터).

**(2)** `StockIdRangePartitioner` 생성:

```java
@Component
@RequiredArgsConstructor
public class StockIdRangePartitioner implements Partitioner {
  private final EntityManagerFactory emf;

  @Override
  public Map<String, ExecutionContext> partition(int gridSize) {
    // 1) SELECT MIN(id), MAX(id) FROM Stock
    // 2) (max-min+1)을 gridSize 등분
    // 3) 파티션마다 ctx.putLong("minId"/"maxId"), key = "partition0", ...
  }
}
```

**(3)** 워커 reader + 마스터/워커 스텝:

```java
@Bean
@StepScope
public JpaPagingItemReader<Stock> partitionedStockReader(
    @Value("#{stepExecutionContext['minId']}") Long minId,
    @Value("#{stepExecutionContext['maxId']}") Long maxId) {
  return new JpaPagingItemReaderBuilder<Stock>()
      .name("partitionedStockReader")
      .entityManagerFactory(emf)
      .queryString("SELECT s FROM Stock s WHERE s.id BETWEEN :minId AND :maxId ORDER BY s.id")
      .parameterValues(Map.of("minId", minId, "maxId", maxId))
      .pageSize(CHUNK_SIZE)
      .build();
}

@Bean
public Step stockCandleWorkerStep() {
  return new StepBuilder("stockCandleWorkerStep", jobRepository)
      .<Stock, StockDailyCandle>chunk(CHUNK_SIZE, transactionManager)
      .reader(partitionedStockReader(null, null))
      .processor(stockCandleItemProcessor)
      .writer(stockCandleItemWriter)
      .listener(stepMonitorListener)
      .build();
}

@Bean
public Step stockCandleStep() {   // 기존 스텝을 마스터로 교체
  return new StepBuilder("stockCandleStep", jobRepository)
      .partitioner("stockCandleWorkerStep", stockIdRangePartitioner)
      .step(stockCandleWorkerStep())
      .gridSize(4)
      .taskExecutor(new ThreadPoolTaskExecutorBuilder()
          .corePoolSize(4).maxPoolSize(4).threadNamePrefix("candle-part-").build())
      .build();
}
```

**(4)** 개선 후 예측치 먼저 기록: `기존 스텝 시간 ÷ gridSize × 1.2(오버헤드)`

**확인**: `candle-part-1..4` 스레드 동시 실행, 메타테이블에 `partition0..3` 생성,
**API 429/거부 없는지** (있으면 gridSize 낮추고 그 사실도 기록).

**면접 카드**: 파티션별 ExecutionContext 독립 → 실패 파티션만 재시작 가능
(멀티스레드 스텝은 재시작 보장 깨짐 — 이 차이를 설명할 수 있어야 함).

### 1-5. 카드 D — Keep-Alive / 커넥션 풀 (1-2에서 지목됐을 때만)

## STEP 2. SSE 부하 측정 (예상 1일, 관제 포지션 직격)

> **사전 확정된 개선 없음.** 2-5 가설 판별 전에는 서버 코드를 고치지 않는다 (측정 장치 제외).

### 2-1. 측정 장치 (1시간)

local 전용 테스트 컨트롤러 (`apps/stock-realtime`):

```java
@Slf4j
@Profile("local")
@RestController
@RequiredArgsConstructor
@RequestMapping("/loadtest")
public class LoadTestController {

  private final SseEmitterRegistry registry;

  @GetMapping(value = "/subscribe", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
  public SseEmitter subscribe() {
    return registry.create("loadtest");
  }

  @PostMapping("/broadcast")
  public String broadcast(@RequestParam(defaultValue = "60") int count,
                          @RequestParam(defaultValue = "1000") long intervalMillis)
      throws InterruptedException {
    for (int i = 0; i < count; i++) {
      long t0 = System.nanoTime();
      registry.broadcast("loadtest", "tick",
          Map.of("seq", i, "sentAt", System.currentTimeMillis()));
      log.info("broadcast seq={} took={}ms", i, (System.nanoTime() - t0) / 1_000_000);
      Thread.sleep(intervalMillis);
    }
    return "done";
  }
}
```

- `sentAt` = 지연 계산 기준, `broadcast took` = 서버 측 루프 소요 (가설 H1 판별 데이터)
- 실시세(장중) 의존 없이 재현 가능한 측정 채널

### 2-2. 부하기 — `scripts/SseLoadTest.java` (2시간)

```
실행: java scripts/SseLoadTest.java <URL> <연결수>
구조:
 - HttpClient 1개, 연결수만큼 sendAsync(..., BodyHandlers.ofLines())
 - 각 라인에서 "sentAt" 파싱 → (현재시각 - sentAt)을 ConcurrentLinkedQueue에 수집
 - 연결 성공/실패 카운트, 종료 시 p50/p95/p99/max 출력
 - 같은 머신이라 clock skew 없음
```

```bash
ulimit -n 65535     # 부하기 셸에서 (책 8장: 도구의 FD 한계)
```

```bash
./gradlew :apps:stock-realtime:bootRun    # 서버 (별도 터미널)
```

  이후 측정은 그 한계의 70% 이하에서만 유효.
  (책 10장 실증: JMeter 7,000rps vs ab 11,088rps — 도구가 천장이면 측정 전부 무효)

| 단계 | 연결 성공/실패 | p50/p95/p99(ms) | broadcast took(ms) | 힙/스레드 |
|---|---|---|---|---|

### 2-5. 가설 판별표 — 측정 결과를 대입

| 가설 | 이 그림이 나오면 확정 | 확정 시에만 하는 처방 |
|---|---|---|
| H1 순차 send 누적 | `took` ≈ send1건 × N으로 선형 증가, p95도 비례 | 브로드캐스트 병렬화 실험 |
| H2 느린 클라이언트 블로킹 | 느린 클라 1개 의도 투입 → p95 급등 | send 격리/타임아웃 |
| H3 직렬화 반복 비용 | payload 10배 → took 비례 증가 | 직렬화 1회 후 재사용 |
| H4 서버 리소스 한계 | 연결 실패율↑, FD/스레드/힙 고갈 | 리소스 튜닝, 이상은 수평 확장 |
| H5 부하기 병목 | 부하기 CPU 포화, 자체 한계 근처 | 측정 무효 — 연결 수 낮춰 재측정 |

**두 개 이상 걸리면 분리 실험. 판별 없이는 개선 금지.**

### 2-6. 확정된 처방 1개 구현 → 동일 시나리오 재측정 → before/after

### 2-7. 변곡점과 확장 로드맵 (문서, 반나절)

- 변곡점 = p95가 목표선을 넘기 시작한 연결 수 → "인스턴스 1대당 안정 구독 ○○○개"
- 로드맵 1페이지: 수신(WebSocket)/서빙(SSE) 분리 + pub/sub 팬아웃 구조도,
  `목표 규모 ÷ 1대 용량 = 필요 인스턴스 수` 계산. **구현하지 않은 범위 명시.**
- 이것이 면접의 "로봇 2.5만 대면?" 답변: 실측 기반 확장 설계

## STEP 3. 캔들 복합 인덱스 (조건부 — 계산 스텝/쿼리 병목일 때)

현황: `StockDailyCandle`에 인덱스 정의 없음. stock_id는 FK 자동 인덱스, **trade_date 미인덱스**.

1. p6spy(또는 show_sql + 시간 로깅)로 MA/RS 스텝 실제 SQL 캡처
2. Before:
   ```sql
   EXPLAIN ANALYZE SELECT ... FROM stock_daily_candle
   WHERE stock_id = ? AND trade_date BETWEEN ? AND ?;
   ```
   `type=ALL` 여부, rows 캡처 저장
3. 인덱스 추가:
   ```java
   @Table(indexes = @Index(name = "idx_candle_stock_trade_date",
                           columnList = "stock_id, trade_date"))
   ```
   - 컬럼 순서 근거 기록: 등치(stock_id) 선행, 범위(trade_date) 후행
   - 로컬은 ddl-auto create라 반영. 운영용 `CREATE INDEX` DDL 별도 기록
4. After: 동일 SQL (`type=range` 확인) + 실행시간
5. **배치 재실행**으로 계산 스텝 단축까지 기록되면 스토리 완성

**✅ 완료 조건**: EXPLAIN before/after + 쿼리 시간 + (가능하면) 배치 스텝 단축률. PR `perf/candle-index`.
